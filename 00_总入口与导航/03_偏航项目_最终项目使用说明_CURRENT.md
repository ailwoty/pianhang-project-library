## 四、权威与真值的日常判断方法

不得仅凭文件名中的`CURRENT / FINAL / 正史 / 终版`判断权威。

任何信息至少判断：

1. 来源是谁；
2. 指令强度有多高；
3. STORY_STATUS是什么；
4. TRUTH_STATE是什么；
5. 是否已经通过合法事务COMMITTED；
6. 当前领域真正的权威入口是哪一个stable object。

项目级默认裁决顺序：

`用户当前明确指令`
→ `根级最高前置指令确定执行边界`
→ `对应领域真正CURRENT/CANON源`
→ `已COMMITTED正文与运行态`
→ `章节合同/滚动规划`
→ `CANDIDATE/WORKING`
→ `HISTORY/AUDIT/LEGACY`
→ `REFERENCE`

该顺序不是简单的“后一层永远更低”。必须保留领域边界：

- 执行规则不能自行创造故事事实；
- 人物主档不能无事务覆盖已经COMMITTED的剧情变化；
- 运行态不能自行改写不可变世界锁；
- 计划/合同是未来目标，不等于已经发生；
- `OPEN / UNKNOWN / UNOBSERVED / NOT_COMMITTED`不得被旧稿、常识或模型推断静默填值；
- 用户明确要求RETCON时授权层最高，但持久化仍必须走合法修订/事务流程。

## 五、新建与修改文件的长期规则

### 5.1 先判断是否真的需要新文件

同职责已有CURRENT/stable object时，默认原位更新。禁止通过：

- `最终版2`；
- `FINAL_FINAL`；
- `CURRENT_NEW`；
- 仅靠日期更晚；

制造第二CURRENT。

### 5.2 新文件必须先过六个路由判断

1. NEED：是否必须新建；
2. DOMAIN：唯一业务域在哪里；
3. STATUS：CURRENT/CANON/CANDIDATE/WORKING/AUDIT/HISTORY/BLOCKED/OPEN中的哪一种；
4. CONFLICT：是否与既有同职责文件冲突；
5. PERSISTENCE：是否需要事务、注册、依赖/PREWRITE处理；
6. INDEX：创建后需要同步哪些索引/矩阵/入口。

无法确定合法落点时默认`HOLD`，不得“先随便放”。

### 5.3 任何新建或修改必须有文件使用说明

至少写清：用途、原因、内容边界、权威状态、上游依赖、后续调用方式、与其他文件关系、禁止误用；修改文件还必须说明改了什么、没改什么、影响范围和兼容关系。

### 5.4 新建/修改后强制回读

至少核验：

- 路径；
- stable `library_file_id`；
- 状态；
- 是否形成第二CURRENT；
- 是否同步必要索引；
- 是否错误进入V12 56个stable object；
- 是否改变53项PREWRITE依赖或使当前PREWRITE失效；
- 是否保留历史证据。
