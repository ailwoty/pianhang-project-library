## 1. 正确流水线
0. READ_GUARD：读取事务日志根锚，确认无其他非终态租约；失败即HOLD。
1. LOAD_CONTROL：读取当前执行入口、硬锁、schema。
2. LOAD_STORY：读取当前快照、相关人物、关系历史、伏笔、世界状态、开放问题。
3. VALIDATE_INPUT：检查版本、缺失依赖、冲突。
4. PRE_WORLD_SIM：只推演`WORLD_CLOCK_START`之前已激活过程与本章同期但不依赖未发生正文选择的候选。
5. BUILD_CHAPTER_PLAN：结合人物/关系/世界候选形成章节方案。
6. 7K_RECALL：有自然关系窗口才召回0—3个机制。
7. DRAFT：写正文草稿，仍非S1A。
8. REVIEW：文风/人物/情绪/因果/原创与四级Gate。
9. STAGE_STATE：生成事实、事件、资源、情报、关系等delta，但暂不提交；对尚未存在的节点只使用`TMP_*`本地临时引用，不预猜FACT/EVT/INFO/HOOK等正式编号。
10. POST_WORLD_SIM：只基于草稿中真实发生动作推演余波候选。
11. VALIDATE_TRANSACTION：一致性、临时引用闭合、既有稳定ID引用、时间、重大节点、闭世界、权限检查；此时不得以“先占号”方式创建新正式运行ID。
12. ACQUIRE_WRITE_GUARD / PREPARE：先联查事务日志与当前快照，确认不存在**其他**`PREPARED/PARTIAL_FAILURE`写事务；随后为事务身份选择COMMIT_ID，并在首次CHAPTER时选择CHAPTER_UID，连同基准快照、目标集合、版本前置条件与临时引用摘要写入事务日志。**PREPARED记录成功持久化并回读通过的瞬间才完成COMMIT_ID/R###与首个CHAPTER_UID的正式保留**；该步失败则这些事务身份未完成持久分配，也禁止触碰任何目标文件。
13. ALLOCATE_IDS_AND_COMMIT_BODY_AND_STATE：仅在PREPARED租约回读成功后，由同一COMMIT把`TMP_*`映射为正式稳定ID/局部revision并先持久登记`ID_ALLOCATION_MANIFEST`；登记回读通过后，才写入正文、状态delta、正式正文索引候选行、当前状态快照、相关稀疏运行账、滚动三章计划与世界checkpoint索引。若`BASE_ROLL_FORWARD_REQUIRED=YES`，当前快照这一次写入必须先把上一有效COMMITTED候选压实为`MATERIALIZED_BASE=BASE_SNAPSHOT_ID`，再写本事务PREPARED_CANDIDATE；不得让新候选覆盖仍未物化的上一有效CURRENT。此时事务日志仍不得标`COMMITTED`。
14. VERIFY_TARGET_WRITES：回读所有必写目标，核对稳定ID/版本/COMMIT_ID/引用完整性，并再次确认写租约仍属于本COMMIT。
15. FINALIZE_COMMIT_LOG：仅在14全部PASS后，把**同一条已存在的PREPARED/PARTIAL_FAILURE记录**最后更新为`COMMITTED`。事务日志是最终正史开关。
16. VERIFY_COMMIT：重新核对“正文索引有效COMMITTED行 + CURRENT_COMMIT_ID（读时派生）+ 事务日志COMMITTED + EFFECTIVE_CURRENT_SNAPSHOT_ID=RESULT_SNAPSHOT_ID”一致。
17. PUBLISH_SNAPSHOT：只发布已提交事实的派生checkpoint/下一章加载包，不在此阶段新增或改写本章客观事实。

## 2. 两阶段提交
### PREPARE
本节主路径只适用于`TYPE=CHAPTER / CHAPTER_REVISION`；`TYPE=CANON_BASELINE`与`TYPE=MAINTENANCE`分别走下方独立分支。
生成：
- TRANSACTION_TYPE：`CHAPTER / CHAPTER_REVISION`
- COMMIT_ID
- BASE_SNAPSHOT_ID：必须冻结为PREPARE开始时联查得到的`EFFECTIVE_CURRENT_SNAPSHOT_ID`；不得用滞后的MATERIALIZED_BASE代替
- RESULT_SNAPSHOT_ID：章节事务固定`SNAP_<CHAPTER_UID>_R###`，由本次`CHAPTER_UID + R###`确定性派生并随PREPARED日志行一并保留；不进入后置`ID_ALLOCATION_MANIFEST`
- BASE_ROLL_FORWARD_REQUIRED：YES/NO；当上一有效CURRENT仍位于旧候选槽且本事务需复用该槽时=YES
- EXPECTED_FILE_VERSIONS（工具提供`current_version_number`时）
- BASE_CONTENT_TOKENS（版本号不可得时：stable library_file_id + 当前file_id/version_id/modified_at + HASH_IF_AVAILABLE）
- CONCURRENCY_MODE：OPTIMISTIC_VERSION_LOCK / COMPARE_BEFORE_WRITE_FALLBACK
- PREPARED_PAYLOAD_FINGERPRINT：章节/章节修订必填，格式`SHA256_UTF8_CANONICAL_JSON_PAYLOAD_V2:<64-lowercase-hex>`；冻结正文+staged sparse delta+章节语义元数据+LOCAL_TEMP_SCOPE+LOCAL_TEMP_REF_MAP+目标角色集合
- STATE_DELTA_LIST
- WORLD_DELTA_LIST
- OPEN_ISSUE_DELTA
- PREVIOUS_ATTEMPT_COMMIT_ID（仅新R###承接上一ABORTED尝试时）
- SUPERSEDES_COMMIT_ID（仅拟替代既有COMMITTED正史时）
- LOCAL_TEMP_SCOPE（事务日志独立一等字段；CHAPTER/CHAPTER_REVISION=`WORKING_<LOCAL_TOKEN>`，CANON_BASELINE=`BASELINE_<LOCAL_TOKEN>`，MAINTENANCE=`N_A`；首次PREPARED后冻结且历史scope不得被其他COMMIT复用）
- LOCAL_TEMP_REF_MAP（事务日志独立一等字段；只列TMP候选摘要；候选联合键=`LOCAL_TEMP_SCOPE + TEMP_REF`；无新TMP写`NONE_NO_NEW_TEMP_REFS`）
- ID_ALLOCATION_MANIFEST（PREPARED租约成功后写入；正式ID/局部revision分配清单）
生成上述内容后，必须**先把事务日志中的本COMMIT记录持久写为`PREPARED`并回读确认**，再开始任何BODY/DELTA/运行账写入。



### PREPARED_PAYLOAD_FINGERPRINT｜P406 / P419—P420
同一事务允许从`PARTIAL_FAILURE`继续的前提不能只靠“看起来没改”。`CHAPTER/CHAPTER_REVISION`首次PREPARED必须持久化一等字段`PREPARED_PAYLOAD_FINGERPRINT`。

当前唯一规范算法：`SHA256_UTF8_CANONICAL_JSON_PAYLOAD_V2:<64-lowercase-hex>`。旧`SHA256_UTF8_LF_CANONICAL_PAYLOAD_V1`在正式第一章尚未发生前即停止新写，只保留历史治理文本兼容；不存在需要迁移的已提交章节指纹。

#### V2规范对象
先构造且只构造以下顶层JSON对象，键名固定：
- `schema`：固定字符串`PREPARED_PAYLOAD_V2`
- `body`
- `chapter_meta`
- `staged_delta`
- `local_temp_scope`
- `local_temp_ref_map`
- `target_role_set`

`body`：
- 把CRLF/CR统一为LF；
- 保留其余全部字符、空格、段落与**末尾LF是否存在**；
- 不trim、不做Unicode NFC/NFD等规范化；初始UTF-8 BOM不得进入字符串。

`chapter_meta`：
- `chapter_meta`的键集合**恰好**为：`TITLE / POV / ORDER_KEY / DISPLAY_NO / WORLD_CLOCK_START / WORLD_CLOCK_END / WALL_CLOCK_START_LOCAL / WALL_CLOCK_END_LOCAL / TRANSACTION_TYPE / BASE_SNAPSHOT_ID / PREVIOUS_ATTEMPT_COMMIT_ID / SUPERSEDES_COMMIT_ID`；禁止自行增加、删除或重命名键；
- `chapter_meta`不允许由实现自行选择空值哨兵。逐键规范：
  - `TITLE`：写本事务冻结的确切标题字符串；若章节明确无标题只能写`NONE`；禁止`UNKNOWN/N_A`与空字符串。
  - `POV`：写确切POV标识；禁止任何空值哨兵与空字符串。
  - `ORDER_KEY`：无符号十进制规范字符串；除`0`外禁止前导零、正号或其他等价写法。
  - `DISPLAY_NO`：无符号十进制规范字符串；除`0`外禁止前导零、正号或其他等价写法。
  - `WORLD_CLOCK_START / WORLD_CLOCK_END`：必须是当前世界时钟规范token；禁止`UNKNOWN/NONE/N_A`。
  - `WALL_CLOCK_START_LOCAL / WALL_CLOCK_END_LOCAL`：有可靠精确钟点时写规范本地时刻字符串；未锁定时**固定写`UNKNOWN`**，禁止`NONE/N_A`。
  - `TRANSACTION_TYPE`：只允许`CHAPTER / CHAPTER_REVISION`。
  - `BASE_SNAPSHOT_ID`：必须写本事务冻结的实际snapshot ID；禁止空值哨兵。
  - `PREVIOUS_ATTEMPT_COMMIT_ID`：存在前次ABORTED尝试时写其COMMIT_ID，否则**固定写`NONE`**。
  - `SUPERSEDES_COMMIT_ID`：修订既有COMMITTED正史时写被替代COMMIT_ID，否则**固定写`NONE`**。
- `N_A`只用于事务日志中“不适用”的维护/历史字段，**不得出现在V2 `chapter_meta`**；上述键之外也不得新增其他scalar键。
- `COMMIT_ID / CHAPTER_UID / RESULT_SNAPSHOT_ID / BODY_REVISION / 正式运行ID / Library file_id/version token`不进入V2语义对象，它们由租约与后置分配清单审计。

`staged_delta`：
- JSON object的键只允许是05模板实际产生且**至少含1条记录/1个持久标量变化**的delta section名；空section必须省略，禁止“可写可不写”；
- 每个section的记录数组按`TEMP_REF`（新候选）或既有稳定主ID的UTF-8字节序升序；同section出现重复排序键立即HOLD；
- 记录object使用规范字段名；所有标量转字符串；集合语义数组按UTF-8字节序排序，叙事/时序上明确有序的数组保留原顺序；
- 禁止用自然语言拼接块替代结构化字段以逃避canonicalization。

`local_temp_scope`：精确写事务拟持久的`WORKING_<LOCAL_TOKEN>`字符串。

`local_temp_ref_map`：
- 无新TMP时固定为空数组`[]`；
- 有TMP时每项只含`TEMP_REF / INTENDED_NAMESPACE / LOCAL_SEMANTIC_ROLE / PLANNED_TARGET_LEDGER`四键，按TEMP_REF UTF-8字节序升序；重复TEMP_REF立即HOLD。

`target_role_set`使用固定角色编码并按UTF-8字节序升序：
- `BODY`
- `DELTA`
- `BODY_INDEX`
- `CURRENT_SNAPSHOT`
- `ROLLING_PLAN`
- `WORLD_CHECKPOINT_INDEX`
- `TXN_LOG`
- `OPEN_ISSUE_LEDGER`（仅实际变更时）
- `RUNTIME_LEDGER:<stable_library_file_id>`（每个实际变更的既有运行账各一项）
- 新建尚无stable ID的持久目标使用`NEW_ARTIFACT_PATH:<canonical /偏航/... path>`。
同一物理目标不得用两个角色别名表示；角色不明即HOLD。

#### V2 JSON字节规范
- 顶层及所有object键按**UTF-8字节序**升序；当前规范键均为ASCII；
- JSON不输出任何可选空白；
- JSON字符串转义必须使用**唯一字节形式**：双引号字符`"`编码为JSON字节`\"`，反斜杠字符`\`编码为`\\`，solidus `/`保持字面`/`不转义；U+0008→`\b`、U+0009→`\t`、U+000A→`\n`、U+000C→`\f`、U+000D→`\r`；其余U+0000—U+001F一律写成`\u00xx`，其中`xx`固定为两位**小写**十六进制。除这些控制字符外禁止可选`\uXXXX`写法，其他Unicode标量直接编码UTF-8；出现孤立surrogate或其他非Unicode scalar立即HOLD。
- 不做Unicode normalization；
- 本规范对象不使用JSON number/float/bool/null；所有标量均为string，集合/记录使用array/object；
- `chapter_meta`必须12键全量存在、逐键使用固定空值/格式规则且禁止`N_A`；不得附加实现私有键。`staged_delta`不得包含空array/空object section；同一逻辑空变化只能编码为“键不存在”。
- 最终UTF-8字节流：**无BOM、无额外前后LF、无尾随空格**；
- 对该字节流计算SHA-256，输出64位小写hex，并加前缀`SHA256_UTF8_CANONICAL_JSON_PAYLOAD_V2:`。

规则：
- 指纹在首次PREPARED日志写入前计算并随该行持久化；`MAINTENANCE`填`N_A`。
- 租约后分配的正式ID/file_id/Library版本号不属于PREPARED语义包；它们由`ID_ALLOCATION_MANIFEST/TARGET_MANIFEST`单独审计。
- `PARTIAL_FAILURE`恢复前必须从原工作载荷按V2重新构造规范对象并重算；算法ID或digest任一不一致、缺失、无法重算，均视为载荷无法证明不变，旧事务必须ABORT并新建R###。
- BODY/DELTA任何语义或文本改动、LOCAL_TEMP_SCOPE/LOCAL_TEMP_REF_MAP改变、目标角色集合改变、章节语义元数据改变都会改变指纹；不得在同一事务内“顺手修文”后继续COMMIT。
- 该指纹证明“事务语义载荷未变”，不替代目标文件写后hash、并发token或正史COMMIT验证。

### LOCAL_TEMP_SCOPE + LOCAL_TEMP_REF_MAP 持久边界｜P405/P406/P411/P414/P415
- `LOCAL_TEMP_SCOPE`与`LOCAL_TEMP_REF_MAP`必须作为**两个独立一等列**在首次PREPARED日志行中持久化并回读，不得只存在于内存/草稿或TARGET_MANIFEST自由文本；CHAPTER/CHAPTER_REVISION的scope=`WORKING_<LOCAL_TOKEN>`，MAINTENANCE=`N_A`。
- 若PREPARE来源包含持久WORKING草稿，必须先验证草稿文件名中的`WORKING_<LOCAL_TOKEN>`、`LOCAL_CHAPTER_HANDLE=<LOCAL_TOKEN>`与`LOCAL_TEMP_SCOPE=WORKING_<LOCAL_TOKEN>`逐字同源；不一致立即HOLD。内存草稿也必须由唯一`LOCAL_TEMP_SCOPE`作为本地候选命名空间。
- 已持久化的非N_A `LOCAL_TEMP_SCOPE`不得被另一COMMIT复用；PREPARED前写租约检查同时扫描scope历史，碰撞即HOLD并在PREPARED前换新LOCAL_TOKEN。
- “不得复用”同时适用于同一逻辑章节：ABORT后的新R###重试虽然继承CHAPTER_UID，也必须fork新WORKING scope；COMMITTED后的CHAPTER_REVISION同样使用新scope。只有原COMMIT处于PARTIAL_FAILURE恢复时继续原scope。
- scope第一次进入PREPARED事务历史即视为消费；旧WORKING文件可以保留为非正史审计，但不得再次喂给另一COMMIT。新事务如沿用其文本，必须先复制/重建到新scope并重新计算PREPARED_PAYLOAD_FINGERPRINT。
- 临时候选联合身份=`(LOCAL_TEMP_SCOPE, TEMP_REF)`；相同TEMP_REF可在不同工作区重复，任何跨工作区读取若缺scope即视为歧义并HOLD。
- 最小条目：`TEMP_REF / INTENDED_NAMESPACE / LOCAL_SEMANTIC_ROLE / PLANNED_TARGET_LEDGER`；它只描述待分配候选，不产生正式ID所有权。
- 无新TMP节点仍要保留scope并写`NONE_NO_NEW_TEMP_REFS`；历史MAINTENANCE无此概念写`N_A`。
- 后置`ID_ALLOCATION_MANIFEST`中每个分配项必须同时回指`LOCAL_TEMP_SCOPE + TEMP_REF`，且namespace/target不冲突；不得在取得租约后凭空新增未声明TMP再分配正式ID。
- 若PREPARED后需要改变LOCAL_TEMP_SCOPE、TMP集合、namespace或语义对象，视为事务载荷变化：旧事务必须ABORT并以新R###重开；PARTIAL_FAILURE恢复不得改图。

### 稳定ID分配租约｜P402
- PREPARE之前新候选只允许`TMP_*`本地引用；不得提前猜/保留`FACT/EVT/INFO/HOOK/PROC/FSW/...`正式编号。
- `COMMIT_ID`、首次`CHAPTER_UID`以及由二者确定性派生的`RESULT_SNAPSHOT_ID=SNAP_<CHAPTER_UID>_R###`是PREPARED行例外：三者的正式保留由PREPARED日志行本身完成；RESULT_SNAPSHOT不走后置自由选号。PREPARED写失败=未完成持久保留；PREPARED成功后R###及其派生快照ID永久占用。
- PREPARED回读成功后，本COMMIT先建立/更新`ID_ALLOCATION_MANIFEST`，将`LOCAL_TEMP_SCOPE + TEMP_REF → ALLOCATED_ID_OR_REVISION`登记到事务日志并回读；**分配清单未持久化不得写使用这些ID的目标文件**。
- 选号时扫描现有账 + 全部历史`ID_ALLOCATION_MANIFEST`；已登记后ABORT的编号也视为已用。
- 分配保护集默认覆盖ID规则中**全部已登记稳定命名空间**、未来新增并完成登记的稳定命名空间，以及`*_REVISION/BODY_REVISION/FACT版本号`等事务拥有局部槽；FACT/INFO/HOOK/PROC等历史列举仅是示例，不是白名单。显式例外仅限PREPARED同步保留的COMMIT/首次CHUID/确定性RESULT_SNAPSHOT、Library平台身份、WORKING/TMP本地句柄、LEGACY_ALIAS与纯引用字段。
- `PARTIAL_FAILURE`继续拥有原分配；`ABORTED`的任何受保护正式ID与局部revision永久烧号。除CHAPTER_UID外，后续重试不得回收失败事务分配的编号。
- 同一逻辑章节在首个PREPARED行成功后永久绑定CHAPTER_UID；后续R###重试/CHAPTER_REVISION沿用。不同逻辑章节禁止借用。
- `BODY_REVISION`在取得租约后与其他局部revision一起预留；ABORT烧号，下一R###使用更高值。
- 已存在的S0/T0/CURRENT ID不重新分配；本规则只约束新分配。
- `LEASE_ROW_PRESERVATION_VERIFY`：从PREPARED落库到最终COMMITTED/ABORTED之前，任何对事务日志文件本身的中间重写都必须保留本COMMIT的非终态租约行、COMMIT_ID/TYPE/PREFLIGHT_IMPACT与当前STATUS；若该行丢失、被改成其他COMMIT或提前变终态，立即HOLD。除非必须修复日志自身，事务日志schema/说明文字变更优先延迟到最终`SELF_COMMITTED_WRITE`一次完成。`PREPARED`不是内存标签，而是失败恢复与单写者保护所依赖的持久记录。
- `TXN_TABLE_CONTIGUITY_VERIFY`：事务日志的22列表头、分隔行与全部`CM_*`事务数据行必须构成**一个连续Markdown表块**；事务行之间禁止插入空行、标题或说明文字。所有说明只能放在完整表块之后。PREPARED/终结写后必须机器校验：每条事务行列数=22、COMMIT_ID唯一、非终态租约≤1、表块中事务行数=全文件`^| CM_`行数；任一不等立即HOLD。

### 单写者写租约
- 当前治理层对会修改CURRENT正文/快照/运行账的事务采用`SINGLE_WRITER`：任一时刻最多允许一个非终态写事务（`PREPARED`或`PARTIAL_FAILURE`）。
- 新事务在写PREPARED记录前必须扫描事务日志；若存在其他非终态写事务，进入HOLD，不得抢占当前快照的`PREPARED_CANDIDATE`槽。
- 同一COMMIT从`PREPARED → PARTIAL_FAILURE`时继续持有租约；只有转为不可逆`COMMITTED`或`ABORTED`后释放。
- 进程中断后若留下PREPARED/PARTIAL_FAILURE，下一次运行必须先恢复/核验该COMMIT或将其合法ABORT；不得直接开启另一个写事务。
- `CM_MAINT_*`只要会改CURRENT持久文件，也服从同一租约；纯只读审计不占写租约。
- 本规则不新增锁文件；事务日志的非终态COMMIT记录就是唯一租约真值源，当前快照`PREPARED_COMMIT_ID`必须与其一致。

状态=`PREPARED`。

### MAINTENANCE事务分支
`TYPE=MAINTENANCE`使用`CM_MAINT_<TOPIC>_R###`，同样必须先取得SINGLE_WRITER租约并写/回读PREPARED日志，但**不进入上面的章节快照推进路径**：
- `CHAPTER_UID / BASE_SNAPSHOT_ID / RESULT_SNAPSHOT_ID / WORLD_CLOCK_START / WORLD_CLOCK_END / CANON_INDEX_VERIFY / CURRENT_SNAPSHOT_VERIFY = N_A`；
- 不创建正文/DELTA，不写正式正文索引，不写CHAPTER_CHECKPOINT，不推进滚动三章的故事事实窗口；
- 可修改schema、provenance、索引、缓存、治理元数据，或在已有故事证据不变的前提下纠正“记录错误”；所有目标仍需TARGET_MANIFEST、并发基准、回读VERIFY和最终COMMITTED；
- 若维护触及当前快照，只允许等价物化/缓存整理，必须证明`CURRENT_COMMIT_ID / EFFECTIVE_CURRENT_SNAPSHOT_ID / WORLD_CLOCK_CURSOR / LAST_COMMITTED_WORLD_CLOCK / LAST_COMMITTED_CHAPTER_UID`逻辑值前后不变；
- 一旦发现需要改变客观FACT/EVT、S1A/S1B、世界时钟或正式正文，立即ABORT/HOLD维护事务，改走`CHAPTER_REVISION`与对应RETCON Gate，禁止“维护名义下写故事”。
- MAINTENANCE必须在事务日志独立字段`PREFLIGHT_IMPACT`声明`INVALIDATES / NEUTRAL_RECORDER`，不得只埋在`TARGET_MANIFEST`自由文本；任何schema/路由/加载/运行语义实质修改默认`INVALIDATES`，只有严格受限的PREWRITE记录事务可标`NEUTRAL_RECORDER`。



### CANON_BASELINE事务分支｜T0前已确认历史基线编译
`TYPE=CANON_BASELINE`使用`CM_BASE_<TOPIC>_R###`，只用于把**已经由用户明确确认或既有上位硬正史逐字锁定、且客观发生在当前故事T0之前**的历史基线编译为V12运行账中的`S0_WORLD_LOCK / TRUE_CANON` FACT/EVT。它不是“候选升格捷径”，也不是章节修订替代品。

硬边界：
- 允许来源：`A0_USER`，或能够逐命题回指到既有已COMMITTED硬正史/CURRENT的等价上位来源；`A6_CANDIDATE`、推断、聊天草案、作者工作假说均不得单独触发。
- 允许目标：新建此前不存在的T0前历史`FACT/EVT`及其必要最小引用；本类型默认**不创建INFO/CLAIM/EVID/KNOW/REL/PROC/CAUS等扩展节点**，需要时另走对应合法事务。
- 禁止用途：修改/删除已有COMMITTED FACT/EVT、重解释已提交章节、改变T0之后的客观故事事实、推进当前世界时钟、改变人物当前权限/关系/资源。前述事项必须走`CHAPTER_REVISION`与RETCON Gate。
- `CHAPTER_UID / BASE_SNAPSHOT_ID / RESULT_SNAPSHOT_ID / WORLD_CLOCK_START / WORLD_CLOCK_END = N_A`；不得生成BODY/DELTA、不得写正式正文索引、不得创建CHAPTER_CHECKPOINT、不得改变`CURRENT_COMMIT_ID / EFFECTIVE_CURRENT_SNAPSHOT_ID / LAST_COMMITTED_CHAPTER_UID / WORLD_CLOCK_CURSOR`。
- 首次PREPARED必须写`LOCAL_TEMP_SCOPE=BASELINE_<LOCAL_TOKEN>`、完整`LOCAL_TEMP_REF_MAP`与`PREPARED_PAYLOAD_FINGERPRINT=SHA256_UTF8_CANONICAL_JSON_PAYLOAD_V2:<hex>`；正式FACT/EVT编号只能在租约回读成功后通过`ID_ALLOCATION_MANIFEST`分配，ABORT烧号规则与章节事务相同。
- `PREFLIGHT_IMPACT`固定=`INVALIDATES`。任何CANON_BASELINE COMMITTED都会使既有PREWRITE/PREFLIGHT失效，后续DRAFT前必须重跑。
- `CANON_INDEX_VERIFY`必须验证本事务创建的全部S0节点均绑定本`CM_BASE_*`且来源命题逐项闭合；`CURRENT_SNAPSHOT_VERIFY`必须验证故事CURRENT四元组完全不变。
- CANON_BASELINE的正史生效条件是：本事务`STATUS=COMMITTED`且对应FACT/EVT自身通过来源、引用与真值校验。它进入“历史基线正史链”，但**不成为项目级章节故事CURRENT提交**。

### MAINTENANCE可变CURRENT目标的PREIMAGE与ABORT回滚
维护事务可能需要原地覆盖稳定`library_file_id`对应的控制/治理文档。此类文件不像章节BODY、append-only revision账那样天然保留一个可直接解析的上一有效候选，因此必须额外执行PREIMAGE保护：
1. **首次覆盖前保存并验证PREIMAGE**：`TARGET_MANIFEST`至少记录目标稳定`library_file_id + PRE_file_id/version_id/modified_at + HASH_IF_AVAILABLE + PREIMAGE_RECOVERY_REF`。规范`PREIMAGE_RECOVERY_REF`优先取覆盖前的`PRE_file_id`；首次覆盖前必须实际执行read/materialize恢复探针并记录`PREIMAGE_RECOVERY_PROBE=PASS`。工具能物化raw bytes时，同时保留本事务精确PREIMAGE。若旧对象不能重新读取/物化，且没有其他持久精确备份，写前HOLD，不得先覆盖。
2. **PREPARED/PARTIAL_FAILURE期间的最新物理版本只是事务内候选**：其他DRAFT/维护工作不得把它当已生效CURRENT；SINGLE_WRITER租约必须持续占用。
3. **COMMITTED时生效**：全部目标VERIFY通过并最终COMMITTED后，本事务写入版本才成为该治理文件的有效CURRENT。
4. **ABORTED_BEFORE_TARGET_WRITES**：若尚未触碰任何目标，可直接ABORT，无需恢复。
5. **写过目标后不得直接ABORT**：必须先把每个被原地覆盖的可变稳定文件恢复到PREIMAGE内容，确认稳定`library_file_id`不变并回读内容/hash一致；`TARGET_MANIFEST`记录`ROLLBACK_VERIFY=PASS`后，才允许把事务终结为ABORTED。
6. **恢复不完整时不能释放租约**：任何目标无法恢复或回读不一致，事务保持`PARTIAL_FAILURE/MAINTENANCE_BLOCK`，禁止标ABORTED/COMMITTED，直到恢复或完成原事务。
7. 对不可变新artifact、append-only revision候选等不会遮蔽上一有效状态的目标，可保留失败候选并由事务状态判无效，不要求物理删除。
8. 事务日志自身是恢复锚点，不通过“回滚删除记录”恢复；其PREPARED/PARTIAL_FAILURE/COMMITTED/ABORTED历史必须保留。

### COMMIT
所有必需写入均成功才把COMMIT_ID标记`COMMITTED`。
任一必需写入失败：
- 不把章节标为FINALIZED；
- 不把任何候选事实当S1A/S1B继续使用；
- 若只是部分目标写入/验证失败、正文与delta载荷完全不变且基准可重新验证：状态=`PARTIAL_FAILURE`，允许继续**同一个事务**补齐缺失目标；
- 若正文/delta/目标集合/基准语义需要改变，或无法证明原载荷未变：状态=`ABORTED`，该COMMIT终结，禁止再转COMMITTED；后续分配新的`R###`，用`PREVIOUS_ATTEMPT_COMMIT_ID`引用被终止尝试；若同时是对既有正史的正式修订，另用`SUPERSEDES_COMMIT_ID`指向被替代的旧COMMITTED；
- 禁止为了绕开失败另开一个内容相同但未建立关联的平行事实线。

工具层不能保证真正数据库原子事务，因此用“提交日志+版本前置条件+最终验证”实现工程原子性。

### 必写目标集合与终结顺序
PREPARE时`TARGET_FILES`至少声明：
1. 正文`V12正文_<CHAPTER_UID>_R###.md`；
2. 状态delta`V12状态_<CHAPTER_UID>_R###_DELTA.md`；
3. 正式正文索引；
4. 当前状态快照寄存器（若单槽复用则先把事务开始时的EFFECTIVE_CURRENT roll-forward为MATERIALIZED_BASE，再写PREPARED_CANDIDATE）；
5. 本章发生变化的稀疏运行账；
6. 滚动三章计划；
7. 世界快照索引中的CHAPTER_CHECKPOINT；
8. 开放问题/冲突登记（仅有变化时）；
9. 事务提交日志。

终结顺序不是“最后才第一次写事务日志”，而是：
A. **先写并回读事务日志PREPARED记录，取得SINGLE_WRITER租约**；
B. 再写1—8并回读验证；
C. 最后只把同一日志记录的状态更新为`COMMITTED`。
若A失败，1—8一个都不能写；若B失败，日志保持PREPARED/PARTIAL_FAILURE/ABORTED并继续阻止其他写事务抢占。
任何候选文件在事务日志COMMITTED前，不得被下一章当S1A/S1B或CURRENT正史使用。
对所有带`*_REVISION`的可变运行节点，COMMIT_BODY_AND_STATE必须**追加候选revision并保留上一条有效revision**；不得以“文件有Library版本史”为理由原地覆盖旧有效状态。VERIFY_TARGET_WRITES必须检查旧有效revision仍可解析。
滚动计划、CHAPTER_CHECKPOINT、当前快照候选和正文索引候选的“CURRENT/ACTIVE_CANONICAL”都是**联查事务日志后派生的有效状态**：事务日志COMMITTED最后落笔即完成正史生效，不要求随后再对这些文件做一次必要覆盖写。若以后物化状态标签/压实基线，只能作为读优化。

`PUBLISH_SNAPSHOT`不承担上述必写状态的首次落库；它只生成/刷新读优化的派生加载包。若发布失败，登记MAINTENANCE_BLOCK并在下一章LOAD前修复，但不得伪造第二条事实线。

### 失败恢复状态机
允许转换：
- `PREPARED → COMMITTED`：正常路径；
- `PREPARED → PARTIAL_FAILURE → COMMITTED`：仅限载荷完全不变、失败目标补齐、全部基准重新验证后；
- `PREPARED/PARTIAL_FAILURE → ABORTED`：发现载荷变化、并发基准失效、目标集合需要重编或决定放弃时；若MAINTENANCE已经原地覆盖可变CURRENT目标，必须先完成PREIMAGE恢复并取得`ROLLBACK_VERIFY=PASS`，否则只能保持PARTIAL_FAILURE/HOLD；
- `ABORTED`为终态，不能再转COMMITTED；
- `COMMITTED`同样是不可逆终态；后续修订若成功，由新COMMITTED记录的`SUPERSEDES_COMMIT_ID`指向旧COMMIT，旧行仍保持COMMITTED。

`PARTIAL_FAILURE`恢复必须记录`RECOVERY_COUNT / FAILED_TARGETS / REVALIDATED_BASE_TOKENS / PAYLOAD_FINGERPRINT_REVERIFY`；其中重算指纹必须等于原`PREPARED_PAYLOAD_FINGERPRINT`。
若失败目标涉及revisioned ledger，恢复前还必须确认上一有效revision未被候选覆盖/删除；否则不得继续同一事务为COMMITTED，需先修复账内历史完整性。
若修复过程中改了正文、delta或任何会改变事实含义的字段，必须ABORT旧COMMIT并创建新`CM_<CHAPTER_UID>_R###`；新事务用`PREVIOUS_ATTEMPT_COMMIT_ID`串接失败尝试。若该新事务还在修订既有已提交正文，则`SUPERSEDES_COMMIT_ID`继续指向真正被替代的旧COMMITTED，而不是指向ABORTED尝试。

## 3. 版本前置条件与工具降级

### 首选：OPTIMISTIC_VERSION_LOCK
工具能返回`current_version_number`时必须：
- 使用稳定`library_file_id`识别目标；
- 写前实时读取`current_version_number`；
- 上传时带`expected_current_version`；
- 冲突则重新读取并合并，禁止盲覆盖。

### 回退：COMPARE_BEFORE_WRITE_FALLBACK
若当前工具/表面**不返回可用的`current_version_number`**，不得伪造版本号，也不得因此取消并发检查。改用：
1. 写前按稳定`library_file_id`读取目标，冻结当前`file_id`、`version_id`（若有）、`modified_at`和`HASH_IF_AVAILABLE`；
2. 完成补丁后、真正覆盖前再次刷新同一稳定ID；若基准令牌发生变化，立即HOLD并重新读取/合并；
3. 只有基准未变才允许同路径覆盖；覆盖后必须确认`library_file_id`保持不变；
4. 回读内容、COMMIT_ID、关键锚点和新版本对象；任何不一致进入`PARTIAL_FAILURE/MAINTENANCE_BLOCK`；
5. 该模式只是工程级compare-before-write，**不是数据库原子CAS**。存在并发歧义时事务日志不得终结为COMMITTED。

#### FALLBACK_LEASE_FENCE｜P427
当`CONCURRENCY_MODE=COMPARE_BEFORE_WRITE_FALLBACK`时，SINGLE_WRITER只能视为“可检测租约”，不能假装成原子互斥；必须增加逐目标围栏：
1. PREPARED写入并回读成功后，执行者记录本次回读得到的当前事务日志物理对象作为`LEASE_FENCE_LOG_OBJECT`（file_id/version_id/modified_at，能取多少记多少）。该值是执行期围栏证据，不要求为了把self file_id写回同一PREPARED行而再改一次日志。
2. **禁止对两个或以上可变稳定目标做同一次批量覆盖**。每个可变目标必须单独写；新建不可变artifact可在不共享旧CURRENT的前提下另行处理。
3. 每个可变目标写入**立即之前**都要按稳定事务日志ID重新读取：本COMMIT行必须仍存在、状态只能是`PREPARED/PARTIAL_FAILURE`、全表不得出现第二个非终态租约，且当前日志对象必须与本执行者最近一次成功围栏读取一致。任一不满足即`LEASE_LOST`，该目标不得写。
4. 每个目标写入**立即之后**再次读取事务日志做同样检查；通过后才允许进入下一个目标。围栏读取本身若看到日志对象变化，必须先解释变化来源；无法证明是本COMMIT自己的合法日志写则按`LEASE_LOST`处理。
5. `LEASE_LOST`后立即停止后续目标写与最终COMMIT。已经原地覆盖的目标必须按PREIMAGE恢复规则登记为待恢复；若当前存在另一非终态租约，不得抢写事务日志或其目标，先HOLD到该租约终结，再恢复本事务已触碰目标并把丢失事务历史补登记为ABORTED/LEASE_LOST。
6. 在fallback模式下，VERIFY必须能列出每个可变目标的`PRE_FENCE_LOG_OBJECT / POST_FENCE_LOG_OBJECT`；缺一即不能COMMITTED。
7. 如果工具重新提供可靠`current_version_number + expected_current_version`原子前置条件，优先回到`OPTIMISTIC_VERSION_LOCK`；P427围栏仍可作为额外校验，但不替代真正CAS。

无论使用哪种模式，PREPARE都必须记录实际使用的`CONCURRENCY_MODE`。

### 事务日志自身的终结写验证
事务日志既是TARGET又是最终正史/维护开关，存在不可避免的自引用：在把本行写成`COMMITTED`之前，不可能预先知道这次终结写生成的最终`file_id`。
因此：
1. `TARGET_MANIFEST`对事务日志自身可在POST位置写规范哨兵`SELF_COMMITTED_WRITE`，但必须同时保存稳定`library_file_id`和终结前基准令牌；
2. 终结写完成后立即以稳定`library_file_id`回读，验证该COMMIT行的`STATUS / TARGET_MANIFEST / COMMIT_FINALIZED_AT`及稳定身份；这个**外部回读结果**就是事务日志自身的写后对象验证；
3. 禁止为了把刚得到的final `file_id`塞回同一COMMITTED行而再做一次必要覆盖；那会破坏“COMMITTED终态最后落笔”原则；
4. 其他目标仍必须在COMMITTED前获得明确写后对象/稳定ID并完成VERIFY，不能滥用`SELF_COMMITTED_WRITE`逃避验证。

## 4. 快照
- ROLLING_SNAPSHOT_REGISTER：双槽寄存器。MATERIALIZED_BASE保存上一份已确认COMMITTED的完整基线；PREPARED_CANDIDATE保存本事务RESULT_SNAPSHOT候选。候选不得覆盖基线。
- RESULT_SNAPSHOT_ID：章节提交结果快照，格式`SNAP_<CHAPTER_UID>_R###`，PREPARE即分配并进入事务日志/世界快照索引。
- EFFECTIVE_CURRENT_SNAPSHOT：读取时只联查`TYPE=CHAPTER/CHAPTER_REVISION`故事事务；候选COMMITTED才生效，否则仍读取MATERIALIZED_BASE。`TYPE=MAINTENANCE`永远不推进故事CURRENT。
- CHAPTER_CHECKPOINT：每章提交摘要
- MID_SNAPSHOT：关键中周期结束
- MACRO_SNAPSHOT：卷/宏相位切换
历史checkpoint不得因rolling覆盖而丢失。

## 5. 稀疏delta
不是每章把所有系统字段填一遍。
只登记：
- 可影响后续的事实
- 权限/关系变化
- 资源/情报/舆论变化
- 伏笔生命周期
- 世界事件
- 不可逆/长期代价
无变化字段写`NO_CHANGE`或省略。

## 6. 事实物质性阈值
不为每个端茶、走路、眨眼建立FACT_ID。
满足至少一项才登记持久事实：
- 会限制未来选择
- 影响关系/权限/资源
- 是伏笔/证据/时间线节点
- 会被后文引用
- 形成长期印象/代价
- 重大人物选择

## 7. RETCON
- TYPO_FIX：措辞/标点，不改事实
- RECORD_FIX：状态库登记错误，正文事实没变
- MINOR_RETCON：局部客观事实修订，不触发7A
- MAJOR_RETCON：核心身份、死亡、主线、重大法律/关系等；必须7A/用户确认
任何修订保留旧版本与SUPERSEDES链。


## 8. 正式正文索引强制同步

正式正文身份统一由：
`V12正文运行态_正式正文索引与产物命名_V5.md`
管理。

每次章节COMMIT：
- 创建**本事务专属且不可变**的`V12正文_<CHAPTER_UID>_R###.md`与`V12状态_<CHAPTER_UID>_R###_DELTA.md`；禁止用PREPARE候选覆盖上一COMMITTED事务的BODY/DELTA。
- R###必须与`COMMIT_ID=CM_<CHAPTER_UID>_R###`一致；ABORTED事务的artifact不复用。
- 把本事务BODY/DELTA各自的稳定library_file_id写入正式正文索引；
- 正文/DELTA写`DECLARED_COMMIT_ID`或记录所属COMMIT；索引写候选行；项目级`CURRENT_COMMIT_ID`由事务日志与当前快照/索引联查派生；
- 索引未成功更新时，即使正文文件上传成功，也不得标FINALIZED。

禁止通过文件名中的“定稿/FINAL”单独判断正史。

BODY/DELTA产物规则：
- 正文和DELTA是**按COMMIT追加**的持久artifact，不属于“局部revision在同一文件内追加”的账本类型；
- 候选artifact一旦成功写入，其文件内容不得在另一个COMMIT下改写。若本事务仍是PARTIAL_FAILURE且载荷完全相同，可按同一路径补齐/修复该事务自己的artifact并重新验证；
- 正式修订必须创建新的R### artifact；旧COMMITTED正文/DELTA保持原文件与原stable library_file_id；
- Library版本史只是工具审计层，不承担正史回滚。
