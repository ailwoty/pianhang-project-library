## 稳定ID分配时机与租约所有权｜P402

本节约束**新运行ID何时从“草稿占位”变成项目稳定身份**。不新增ID服务；唯一分配所有权来自事务日志的SINGLE_WRITER写租约。

### PREPARE之前：只允许有作用域的本地临时引用
- 每个DRAFT/STAGE工作区先建立`LOCAL_TEMP_SCOPE=WORKING_<LOCAL_TOKEN>`；它是非稳定工作区作用域，不进入项目稳定ID命名空间，也不占正式编号。
- DRAFT / STAGE_STATE / PRE_SIM / POST_SIM可以在该scope内使用`TMP_<NAMESPACE>_<LOCAL_ORDINAL>`或等价临时引用串联候选，如`TMP_FACT_01 / TMP_INFO_02 / TMP_HOOK_01`。
- 临时候选的完整身份是二元组`(LOCAL_TEMP_SCOPE, TEMP_REF)`；相同`TEMP_REF`字符串可在不同scope中重复，但同一scope内不得指向两个不同语义对象。`LOCAL_TEMP_SCOPE`一旦出现在任何已持久PREPARED/终态事务行中即永久占用，不得被另一COMMIT复用；PREPARED前未持久化的本地scope不产生项目级占用。
- `TMP_*`不是项目ID、不得写入CURRENT运行账/正式索引/事务外持久文件、不得被其他工作区/章节仅凭TEMP_REF裸串引用，也不占用任何正式编号。
- 首次PREPARED必须把`LOCAL_TEMP_SCOPE`与`LOCAL_TEMP_REF_MAP`作为事务日志**两个独立一等字段**持久化并冻结；后续ID分配、恢复和指纹校验均按scope+TEMP_REF联合键。
- 已经存在的S0/T0/CURRENT稳定节点继续直接引用其正式ID；本规则不要求把`EVT_000001—000003`等既有治理基线重新编号。

### WORKING草稿本地身份不变量｜P414/P415
- 规范本地身份是`LOCAL_TEMP_SCOPE=WORKING_<LOCAL_TOKEN>`；若草稿持久化到Library，文件名中的`WORKING_<LOCAL_TOKEN>`、头部`LOCAL_CHAPTER_HANDLE=<LOCAL_TOKEN>`与`LOCAL_TEMP_SCOPE`后缀必须逐字一致。`LOCAL_CHAPTER_HANDLE`只是派生别名，不构成第二身份。
- 任一三方不一致、同一scope指向不同逻辑草稿、或PREPARE时scope与被审核草稿不一致，立即HOLD；不得“选择一个看起来正确的值”继续。
- PREPARE前同一未消费scope允许保存多个本地草稿版本；这些版本仍是同一WORKING工作族，不占CHUID/BODY_REVISION。
- 一旦某个非N_A `LOCAL_TEMP_SCOPE`首次出现在事务日志任一PREPARED/终态COMMIT中，该scope即永久视为`CONSUMED_BY_TRANSACTION_HISTORY`。只有该COMMIT处于PARTIAL_FAILURE恢复时可继续使用原scope；任何新COMMIT（包括ABORT后的重试与COMMITTED后的CHAPTER_REVISION）都必须fork新`LOCAL_TOKEN/LOCAL_TEMP_SCOPE`。
- 已消费WORKING文件可以保留、比较或作为人工参考，但不得再次作为新PREPARE的scope来源；新事务必须从其内容复制/重建到新的WORKING scope，并重新形成完整payload fingerprint。
- PREPARED_PAYLOAD_FINGERPRINT冻结的是本次提交实际正文/完整staged delta/语义元数据与scope/map，而不是“某个WORKING文件名”。WORKING源文件后续变化不会改写已PREPARED事务。

### 事务身份与确定性派生ID例外：PREPARED日志行本身完成保留
- `COMMIT_ID`必须先存在才能建立租约，因此其R###在**事务日志PREPARED记录成功持久化**这一动作中完成正式保留。日志写失败则没有形成可审计分配。
- 首次`TYPE=CHAPTER`的`CHAPTER_UID`同样在该PREPARED记录中首次正式保留；PREPARE之前只能使用逻辑章节工作句柄，不得预猜`CHUID_######`。
- 章节`RESULT_SNAPSHOT_ID=SNAP_<CHAPTER_UID>_R###`是由该PREPARED行中的`CHAPTER_UID + R###`唯一确定的**事务派生ID**，不是从独立SNAP计数器抢号。它与COMMIT/CHUID在同一PREPARED记录中完成保留，不进入后置`ID_ALLOCATION_MANIFEST`；PREPARED失败则未保留，PREPARED成功后因父R###不可复用而自然不可复用。
- 一旦PREPARED行成功落库，`COMMIT_ID/R###`永久占用；ABORT后不复用。`CHAPTER_UID`绑定该**同一逻辑章节**：其后R###重试/修订沿用该CHUID；不同逻辑章节永远不得继承。
- `TYPE=CHAPTER_REVISION`沿用既有CHAPTER_UID；`TYPE=CANON_BASELINE`与`TYPE=MAINTENANCE`均不分配CHAPTER_UID/RESULT_SNAPSHOT_ID。CANON_BASELINE使用`BASELINE_<LOCAL_TOKEN>`作用域并在租约后分配FACT/EVT稳定ID。

### 取得租约之后：正式ID才可分配
1. PREPARED日志回读成功、确认本COMMIT独占租约后，把`TMP_*`映射为正式稳定ID。
2. 分配结果必须先持久登记到同一事务的`ID_ALLOCATION_MANIFEST`，至少记录`LOCAL_TEMP_SCOPE / TEMP_REF / NAMESPACE / ALLOCATED_ID_OR_REVISION / OWNER_COMMIT_ID / TARGET_LEDGER / ALLOCATION_STATE=RESERVED`；该登记成功并回读后，才允许把这些ID写进BODY/DELTA/运行账。
3. 正式编号选择必须同时避开：现有CURRENT/历史账中已出现的ID、事务日志所有历史`ID_ALLOCATION_MANIFEST`中已登记的ID（含ABORTED）、以及本事务已保留项。SINGLE_WRITER保证分配期间没有第二写者；不建立第95套“ID服务”。
4. `PARTIAL_FAILURE`继续由同一COMMIT占有其已登记ID；恢复时不得重新分配另一组编号。
5. **默认保护覆盖**：本文件`ID命名空间`中已经登记的全部项目稳定命名空间，未来新增且进入本节注册表的稳定命名空间，以及`*_REVISION/BODY_REVISION/FACT版本号`等事务拥有的局部不可复用槽，默认全部受同一分配租约、占用扫描、ABORT烧号与PARTIAL_FAILURE续占规则保护；不得把下方或历史文档里的FACT/INFO/HOOK等示例列表解释成穷举白名单。
6. 明确例外只有：①PREPARED行本身同步保留的`COMMIT_ID`、首次`CHAPTER_UID`及确定性派生`RESULT_SNAPSHOT_ID`；②Library/平台分配的`library_file_id/file_id/version_id`；③`WORKING_<LOCAL_TOKEN>`、`LOCAL_TEMP_SCOPE`与`TMP_*`等非稳定本地句柄；④只读LEGACY_ALIAS；⑤只引用既有稳定节点而不创建新身份的引用字段。除这些显式例外，新增稳定命名空间默认自动纳入租约保护。
7. `ABORTED`事务已经登记的任何受保护稳定ID/局部revision槽永久烧号，不得在后续事务重新赋给相同或不同对象；重试时重新分配。
8. 对既有稳定主ID追加`*_REVISION`时，候选revision也属于本事务分配槽：PREPARED后预留；ABORTED后该revision号烧号，下一尝试使用更高revision。
9. `FACT_######_v#`同时遵守基ID与版本号烧号；已登记但ABORTED的`v#`不得重用。

### BODY_REVISION与局部序号
`BODY_REVISION`不是全局ID，但同样属于事务拥有的局部不可复用槽：
- 同一CHAPTER_UID在取得PREPARED租约后预留下一未用BODY_REVISION，并登记在`ID_ALLOCATION_MANIFEST`；
- 若事务ABORT，已登记BODY_REVISION永久跳过；同一逻辑章节下次R###重试沿用CHAPTER_UID但使用新的BODY_REVISION；
- PREPARED日志写入前失败则尚未正式预留BODY_REVISION，不产生“幽灵烧号”。

### ID字段类型
不是所有以`_ID`结尾的字段都创建新命名空间。

1. **主节点/记录ID**：必须使用本文件登记的稳定前缀，例如FACT/EVT/KNOW/BUS/CAST/MCL/FLOW/SIMPROF/IEDGE。
2. **类型化引用字段**：如`HOLDER_ID / OWNER_ID / CURRENT_ENTITY_ID / CLAIMANT_ID / SUBJECT_ID / ORG_ID / SOURCE_ID / FROM_HOLDER_ID / TO_HOLDER_ID / BASE_SNAPSHOT_ID / LAST_CHANGED_BY_FACT_ID / SUPERSEDES_FACT_ID / BELIEF_TARGET_ID / VARIABLE_REF_ID / LAST_CHANGED_BY_COMMIT_ID / SETTLED_BY_COMMIT_ID`，只引用已有节点，不另建“HOLDER/OWNER/SOURCE/VARIABLE”等命名空间；多态引用必须同时提供类型字段或受字段名本身限制。
3. **Library身份字段**：`BODY_LIBRARY_FILE_ID / DELTA_LIBRARY_FILE_ID / SOURCE_LIBRARY_FILE_ID`使用Library提供的稳定`library_file_id`，不属于小说内部ID命名空间。
4. **外部/资产局部ID**：如7K的`VARIANT_ID`，必须与来源资产一起解释；除非显式登记，不得被当成全局小说实体ID。
5. **章节归属**：统一用`CHAPTER_UID`；旧`CHAPTER_ID`只作历史字段别名。
6. **偏航记录引用**：`DEVIATION_FACT_ID`只引用`FACT_TYPE=DEVIATION_RECORD`的既有`FACT_######_v#`；不建立`DEV_*`或`DEVIATION_*`第二命名空间。

### 提交指针字段兼容
`CURRENT_COMMIT_ID`是**项目级逻辑当前提交指针**，只允许由当前快照寄存器 + 正式正文索引 + 事务日志联查解析；它不是每个运行账都要保存的头字段。
多记录运行账使用单条记录`COMMIT_ID/LAST_CHANGED_BY_COMMIT_ID`，必要时仅维护`LEDGER_LAST_CHANGED_BY_COMMIT_ID`，不得复制项目CURRENT指针。
旧交接中的`CURRENT_COMMIT`、旧事实库头部的`CURRENT_CANON_COMMIT`以及事实库曾短暂使用的头部`CURRENT_COMMIT_ID`只作`LEGACY_FIELD_ALIAS`读取。

### 章节正式产物不可变命名
- 正文：`V12正文_<CHAPTER_UID>_R###.md`；状态：`V12状态_<CHAPTER_UID>_R###_DELTA.md`。
- R###必须等于所属`CM_<CHAPTER_UID>_R###`的R###；BODY/DELTA内部`DECLARED_COMMIT_ID`必须匹配。
- 每个章节COMMIT对应独立BODY/DELTA artifact与独立stable `library_file_id`；不得用候选覆盖旧COMMITTED artifact。
- ABORTED事务的文件可保留审计但其路径/R###不复用；新尝试分配新R###。
- Library版本史不是章节正史版本主键；正文索引必须直接保存每个COMMIT所用BODY/DELTA的稳定Library身份。

### 章节旧标识兼容
`CH_####`、`CH0001`等旧章号式标识只允许出现在历史文件名、显示文本或迁移映射中。
新正文、新状态、新FACT/EVENT外键禁止把它们作为章节主键；持久引用统一使用`CHAPTER_UID`。

### 快照ID与生效规则
- T0基线：`SNAP_T0_V5`。
- 章节结果：`SNAP_<CHAPTER_UID>_R###`，与`CM_<CHAPTER_UID>_R###`一一对应。
- `BASE_SNAPSHOT_ID/RESULT_SNAPSHOT_ID`都是类型化SNAP引用。
- 新事务`BASE_SNAPSHOT_ID`必须等于PREPARE开始时的`EFFECTIVE_CURRENT_SNAPSHOT_ID`，不得错误取用滞后的物化基线。
- 当前快照文件物理保存MATERIALIZED_BASE与单一PREPARED_CANDIDATE；候选COMMIT未COMMITTED时不得覆盖/取代BASE的有效性。
- 若单一候选槽要被下一事务复用，而上一有效CURRENT仍位于旧候选槽，则新事务持有写租约后必须在同一次快照写中先把旧有效CURRENT roll-forward为MATERIALIZED_BASE，再写新候选；该roll-forward不改变正史，只保护ABORT回落点。
- `EFFECTIVE_CURRENT_SNAPSHOT_ID`与项目级`CURRENT_COMMIT_ID`均为联查事务日志得到的逻辑结果；可物化缓存，但缓存不是正史开关。

## 引用完整性
提交前检查：
1. 所有引用ID存在或在同一事务中创建。
2. FACT的`SUBJECT_ID`必须引用实体；`OBJECT_VALUE_TYPE=ENTITY_REF/NODE_REF`时`OBJECT_OR_VALUE`必须引用合法稳定ID，SCALAR/TEXT/STRUCTURED_VALUE不得伪造ID。
3. S1B EVENT的`ACTOR_IDS/AFFECTED_ENTITY_IDS/REGION_IDS`端点存在或在同一事务创建。
4. REL边两端人物/组织存在。
5. INFO必须有ORIGIN或明确UNKNOWN来源状态。
6. NARRATIVE必须引用至少一个FACT/CLAIM/INFO。
7. CAUSAL必须引用真实FACT/EVENT，不直接引用S3计划。
8. S1B EVENT的`CAUSE_SEED_REFS/RESOURCE_CHANGE_REFS/INFO_CHANGE_REFS/RELATION_CHANGE_REFS/DISCOVERY_PATH_REFS/LONG_TERM_CONSEQUENCE_REFS`必须引用合法命名空间；客观提交不能只剩自然语言SUMMARY。
9. `TD_*`必须使用`SOURCE_REF_TYPE + SOURCE_REF_ID`引用已成立FACT/EVENT；不得再写混合`SOURCE_FACT_OR_EVENT_ID`。
10. `HOOK_*`的分析文字不得单独作为事实来源；已持久化的关系/世界变化必须通过相应`*_REFS`回指稳定节点。
11. KNOWLEDGE/CLAIM/INFO的`SOURCE_CHAIN_REFS`必须引用稳定节点；对应NOTE/CONTEXT只作解释。INFO的`HOLDER_IDS`必须是实体引用。
12. RESOURCE运行来源分别使用`SOURCE_FACT_IDS/SOURCE_EVENT_IDS`；正文变化不能只靠自然语言来源。
13. ORG/FLOW/CAUS/MCL/REGION的持久状态变化必须递增各自局部revision并绑定`LAST_CHANGED_BY_COMMIT_ID`；来源/成员/地域/驱动力字段必须使用合法稳定引用。
14. EVENT/PROC/FSW/Q/TD/IEDGE/CAST均为稳定ID下的可变节点；持久状态变化必须递增对应局部revision，并由COMMIT或LAST_CHANGED_BY_COMMIT_ID追溯。
15. KNOWLEDGE/ISSUE同样属于稳定ID下的可变状态节点；belief/置信/权限/来源链或ISS状态/解决证据变化必须新增revision。
16. 任一`*_REVISION`候选写入都不得删除/覆盖上一条有效revision；提交前必须能回退解析到旧有效记录。
17. 核心人物持久进程句柄以`CHARACTER_ID + PROCESS_HANDLE_REVISION`版本化；它是PROC/可用性缓存，不得覆盖PROC实例账权威状态。
18. NAR的`ACTOR_IDS`必须引用实体；其revision变化绑定`LAST_CHANGED_BY_COMMIT_ID`。
19. BUS必须使用`SOURCE_REF_TYPE + SOURCE_ID`与稳定`PAYLOAD_REFS`；BUS记录不可原地修订，纠正使用新BUS_ID并指向`SUPERSEDES_BUS_EVENT_ID`。
20. SIMPROF的`EFFECTIVE_CURRENT_SIMPROF_ID/ACTIVE_CANONICAL`必须由事务日志派生；PREPARE不得物理抢写CURRENT。
21. 删除/废止使用状态，不物理复用旧ID。

## 局部修订号语义
`BODY_REVISION / ENTITY_REVISION / RELATION_REVISION / INFO_REVISION / RESOURCE_REVISION / NARRATIVE_REVISION / ORG_STATE_REVISION / FLOW_REVISION / CAUSAL_REVISION / CLUSTER_REVISION / REGION_STATE_REVISION / EVENT_REVISION / PROC_REVISION / FSW_REVISION / QUEUE_REVISION / TIME_DEBT_REVISION / INFO_EDGE_REVISION / CAST_BINDING_REVISION / KNOWLEDGE_REVISION / ISSUE_REVISION / PROCESS_HANDLE_REVISION`属于各自主对象内部的正整数修订号，不是全局ID：
- 初始持久版本从1开始；
- 同一主ID的记录内容变化时单调递增；
- 不跨对象比较大小；
- 不替代`COMMIT_ID`、`SCHEMA_VERSION`或Library自身`version_id/current_version_number`；
- 修订号变化本身不自动制造故事事实，客观变化仍由FACT/EVENT与COMMIT承载。

### 局部revision持久化与事务安全
所有带`*_REVISION`的可变节点统一采用**保留旧revision + 追加候选新revision**，禁止在事务日志COMMITTED之前原地覆盖掉上一条有效revision：
1. 复合持久身份为`(主ID, REVISION)`；REVISION不是新全局命名空间，但必须能区分同一主ID的历史状态。
2. T0/母版编译基线可为`REVISION=1 + COMMIT=NONE`，视为基线有效记录。
3. 章节/维护PREPARE若改变节点，写`REVISION=n+1`候选并保留`n`；候选绑定`COMMIT_ID/LAST_CHANGED_BY_COMMIT_ID`。
4. `EFFECTIVE_CURRENT_REVISION`读取时取“最高且其事务为COMMITTED的revision”；若最新候选为PREPARED/PARTIAL_FAILURE/ABORTED，则继续读取上一条有效revision。
5. ABORTED候选revision永久不复用，可保留作审计；不得把其编号重新赋给不同载荷。
6. COMMITTED后允许做索引/展示层压实，但不得删除仍被历史FACT/快照/提交引用的旧revision。
7. Library文件版本史只是额外审计证据，不能替代账内revision历史；回滚不能依赖“去找上一版文件”。


### COMMIT重试链与正史替代链
- `PREVIOUS_ATTEMPT_COMMIT_ID`只引用同一逻辑工作的上一条`ABORTED`事务，用于解释为何产生新的R###；它不改变正史CURRENT。
- `SUPERSEDES_COMMIT_ID`只引用历史`COMMITTED`事务，表示本事务若COMMITTED将替代其当前有效性；不得指向失败尝试。
- 两字段可同时存在：例如已有R001正史，R002修订尝试ABORTED，R003重试时可写`PREVIOUS_ATTEMPT_COMMIT_ID=R002`且`SUPERSEDES_COMMIT_ID=R001`。
- BASE_SNAPSHOT必须来自当时有效COMMITTED快照链，不得把ABORTED尝试的RESULT_SNAPSHOT当正式基线。

### COMMIT终态与替代链
- `COMMITTED`与`ABORTED`都是不可逆终态；旧COMMIT行不得因为后继修订而改写为`SUPERSEDED`。
- 新修订事务若替代旧提交，在**新COMMITTED记录**上填写`SUPERSEDES_COMMIT_ID`。
- “是否曾正式成立”检查旧COMMIT自身是否COMMITTED；“是否仍为有效当前”再联查是否存在有效后继COMMITTED替代链。
- 这样FACT/正文/运行revision的历史COMMIT证据不会因后继修订被抹掉。

## 派生头部元数据规则｜P426
- 运行账文件头中标记为`*_CACHE / *_HINT / DERIVED_AT_READ_TIME`的字段仅为便利元数据，不构成FACT、CURRENT指针、故事状态或事务终态。
- 其有效值必须能从规范主记录、正式索引、快照链与事务日志重新计算；无法重算时宁可UNKNOWN/缺失，也不得把缓存当主记录。
- 主记录与CACHE/HINT冲突时，缓存无条件失效；禁止通过更新CACHE/HINT反向修改FACT/EVT/PROC/REL/INFO/RES/FSW/ISS等节点。
- CACHE/HINT可被MAINTENANCE等价刷新，但VERIFY必须证明故事CURRENT、记录级COMMIT与局部revision未改变。

## Schema迁移
- `SCHEMA_VERSION`表示不兼容的主兼容版本；只有破坏旧读写兼容的字段/语义变化才提升。
- 同一主版本内的可选字段新增、校验强化、命名澄清，可保持`SCHEMA_VERSION=5`，但必须写`MIGRATION_NOTE/REVISION_NOTE`说明。
- 旧记录不要求补造未知值；缺失字段填UNKNOWN/N_A。
- 不得通过“迁移”把未知补成故事事实。

## 提交ID规则

章节事务：
`CM_<CHAPTER_UID>_R###`

例：
`CM_CHUID_000001_R001`

优点：
- 不依赖日期/时区；
- 一眼可回溯对应章节；
- 同章修订递增R###；
- 不会因为同一天多次提交而依赖不稳定的全局SEQ。

若未来存在不绑定章节的显式维护事务：
`CM_MAINT_<TOPIC>_R###`
只用于治理/记录修复，不制造故事事实。

事务`TYPE`与COMMIT_ID必须匹配：
- `TYPE=CHAPTER`：`CM_<CHAPTER_UID>_R###`，且该CHAPTER_UID尚无既有正式COMMITTED章节正文；
- `TYPE=CHAPTER_REVISION`：`CM_<CHAPTER_UID>_R###`，针对已有正式章节的新R###修订；若成功替代旧正史，`SUPERSEDES_COMMIT_ID`必须指向被替代的COMMITTED章节事务；
- `TYPE=CANON_BASELINE`：只能使用`CM_BASE_<TOPIC>_R###`；仅创建用户/上位硬正史已确认、发生于当前故事T0之前、此前尚未COMMITTED的新`S0_WORLD_LOCK / TRUE_CANON` FACT/EVT。`CHAPTER_UID/BASE_SNAPSHOT_ID/RESULT_SNAPSHOT_ID/WORLD_CLOCK推进=N_A`，不得生成BODY/DELTA或进入正式正文索引；不得修改已有COMMITTED真值；
- `TYPE=MAINTENANCE`：只能使用`CM_MAINT_<TOPIC>_R###`，`CHAPTER_UID/RESULT_SNAPSHOT_ID/WORLD_CLOCK推进= N_A`，不得产生章节BODY/DELTA、不得创建新的故事FACT/EVT真值、不得进入正式正文索引。

项目级逻辑`CURRENT_COMMIT_ID / EFFECTIVE_CURRENT_SNAPSHOT_ID / LAST_COMMITTED_CHAPTER_UID / WORLD_CLOCK_CURSOR`只沿`TYPE=CHAPTER/CHAPTER_REVISION`且`STATUS=COMMITTED`的有效章节故事链解析；`TYPE=CANON_BASELINE`与`TYPE=MAINTENANCE`均不得成为项目级故事CURRENT，也不得推进世界时钟。CANON_BASELINE只通过其COMMITTED状态激活所绑定的T0前S0 FACT/EVT；维护事务造成的合法记录修复仍只由局部`COMMIT_ID/LAST_CHANGED_BY_COMMIT_ID`追溯。


### MAINTENANCE可变文件的有效版本与回滚
- 对没有独立candidate/revision槽、需要原地覆盖稳定`library_file_id`的CURRENT治理文件，PREPARED/PARTIAL_FAILURE期间的最新物理版本只属于持租约事务，不自动成为有效治理CURRENT。
- 写前必须保存可恢复PREIMAGE；COMMITTED才使候选治理版本生效。
- 若维护事务在写过此类目标后终止，必须先恢复全部PREIMAGE并回读验证，再允许STATUS=ABORTED；否则保持PARTIAL_FAILURE/HOLD。
- `ABORTED_BEFORE_TARGET_WRITES`无需恢复；不可变artifact/append-only候选只要上一有效版本仍可直接解析，可由事务状态判无效而不物理删除。
- GATE读取时若发现ABORTED维护事务曾写可变稳定目标但没有`ROLLBACK_VERIFY=PASS`，视为治理完整性阻断，不能进入DRAFT。
